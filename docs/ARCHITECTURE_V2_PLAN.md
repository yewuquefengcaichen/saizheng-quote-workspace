# 赛正报价工作台 V2 架构方案

## 1. 目标

V2 不是推翻现有系统，而是在保留当前可用工作台的前提下，把核心数据和重能力逐步迁到更现代的架构：

- 前端：未来可升级 React + TypeScript
- API：FastAPI
- 数据库：PostgreSQL
- 队列：Redis + Celery
- 图片检索：pgvector + 多阶段召回 / 精排
- 文件与图片资产：本地归档，后续可切 MinIO / S3

---

## 2. 为什么要升级

当前稳定版的 `SQLite + JSON` 适合快速落地，但存在天然边界：

- 商品库与规则散在 JSON，难做统一索引和增量同步
- 图片检索、历史反馈、同步任务都更适合数据库建模
- 后续做多任务、异步、监控、精排时，JSON 路径会越来越重

所以 V2 的核心方向不是“为了高级而高级”，而是：

> 让商品、图片、同步、历史、反馈都进入统一数据层，后续性能优化和架构重构才有抓手。

---

## 3. 模块拆分

### 3.1 工作台层（当前仍是 Flask）

- 上传商品库 / 报价单
- 人工确认与导出
- 文字搜 / 图搜图选品
- 作为过渡层桥接 V2 API / V2 数据

### 3.2 V2 API 层（FastAPI）

- 商品查询
- 同步任务
- 图片检索
- 历史反馈与规则
- 健康检查与后台任务入口

### 3.3 数据层（PostgreSQL）

核心表：

- `products`
- `product_variants`
- `product_images`
- `product_attributes`
- `image_assets`
- `image_embeddings`
- `quote_batches`
- `quote_items`
- `match_feedback`
- `sync_jobs`
- `sync_job_logs`

---

## 4. 图搜图链路

### 当前已落地

- 图片归档
- `phash + dhash` 128 维向量
- pgvector 召回
- Flask 报价台接入上传图片找商品闭环
- 第一轮文本 / 规格精排

### 后续升级

- provider 升级为 CLIP / 更强视觉模型
- 图向量召回后叠加品牌、规格、历史反馈精排
- 引入人工确认数据做学习型 rerank

---

## 5. 商品同步链路

当前没有官方 API，因此现实可行路径分两层：

### 第一层：可立即上线

- 上传或更新 `products.json`
- 手动点击“同步 V2”
- 把最新商品写入 PostgreSQL
- 让报价台图搜图 / 人工搜索逐步直接用数据库结果

### 第二层：后续增强

- 用 Playwright 登录商城后台
- 抓商品列表、详情、图片与分页
- 形成真正的“商城手动同步”任务
- 未来再做差异同步和定时同步

---

## 6. 迁移原则

- 先桥接，再替换
- 先把高价值链路迁到数据库，再迁页面
- 任何时候都保留可回退稳定版
- 数据迁移要有报告、有抽样、有可验证结果
